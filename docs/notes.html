Redis · 01

How Redis stores the like count on Vercel

1. What Redis is

Redis is a key–value database that keeps all its data in memory (RAM), so reads and writes take well under a millisecond. Every value lives under a name (a key), like a giant dictionary:

likes:site        → "1234"      # the total count
like:v:9f2c…e1    → "1"         # "this visitor already liked"

Data in RAM would vanish on restart, so Redis also writes it to disk in the background. Upstash (the hosted Redis we use) handles this for us.

2. How the count is stored

The count is a plain string holding a number. Redis notices it looks like an integer and stores it compactly as one. You never read it, add 1 and write it back yourself. You send one command:

INCR likes:site    # 1234 → 1235, returns 1235

If the key doesn't exist yet, INCR treats it as 0 and makes it 1.

3. Why no click is ever lost

Redis runs commands one at a time, on a single thread. Even if 1,000 requests arrive together, they wait in a queue and each INCR finishes completely before the next starts. So it's impossible for two clicks to both see 1234 and both write 1235.

# what goes wrong with read-then-write (any database):
A reads 1234 · B reads 1234 · A writes 1235 · B writes 1235   → one like lost

# Redis INCR, queued one after another:
A: INCR → 1235 · B: INCR → 1236                               → both counted

4. One like per visitor: SET NX

SET key 1 NX writes the key only if it doesn't exist (NX = "not exists"). The first time a visitor likes, it succeeds; every later try fails. EX 31536000 deletes the key after a year. The visitor key is a hash of IP + browser + a secret, so no real IP is stored.

The check and the +1 must happen together. Redis runs a small Lua script as one uninterrupted step, so nothing can sneak in between:

if redis.call('SET', KEYS[1], 1, 'NX', 'EX', 31536000) then
  return {1, redis.call('INCR', KEYS[2])}   -- new visitor → +1
end
return {0, redis.call('GET', KEYS[2])}       -- already liked → just the count

5. How Vercel talks to it

On Vercel, the API route (/api/likes) runs as a serverless function: it starts for a request, answers and may be shut down right after. A normal Redis client keeps a TCP connection open, and those connections leak or run out when functions keep starting and stopping.

Upstash solves this by accepting Redis commands over plain HTTPS. Each command is one independent web request, so nothing stays open:

Browser ──POST /api/likes──▶ Vercel function ──HTTPS──▶ Upstash Redis
                                 │                       runs the Lua script
        ◀──── { count } ─────────┘◀───── 1235 ───────────┘

The function finds the database through two environment variables that Vercel adds when you connect Upstash from its Marketplace: KV_REST_API_URL (where) and KV_REST_API_TOKEN (the password). They stay on the server and never reach the browser.

In one line

Redis keeps the count in memory as one number, INCR and a Lua script make every update a single uninterruptible step, and Upstash lets short-lived Vercel functions reach it over HTTPS.

Redis · 02

How "one like per visitor" works

1. What the server can actually see

A website never sees your MAC address. It only exists on your local network, and your router swaps it out before traffic reaches the internet. What arrives at the server is:

SignalExampleNotes
IP address49.37.x.xFrom the x-forwarded-for header on Vercel. Shared by everyone on the same Wi-Fi.
User-agentChrome 131 / macOSBrowser and OS. Tells people on the same Wi-Fi apart.

2. Turning them into a visitor ID

The server joins IP + user-agent + a secret (LIKE_SALT) and runs it through SHA-256, a one-way hash:

sha256("49.37.12.8" + "Chrome/macOS" + LIKE_SALT)
  → 9f2c…e1          # same visitor → same ID every time

A hash can't be turned back into the IP. The secret salt matters: without it, someone could hash every possible IP (there are only about 4 billion) and match them up.

3. Locking the like with SET NX

The ID becomes a Redis key. SET … NX writes it only if it doesn't exist yet, and only then does the count go +1:

# first like
SET like:v:9f2c…e1 1 NX EX 31536000   → OK    then INCR likes:site
# any later like from the same visitor
SET like:v:9f2c…e1 1 NX EX 31536000   → nil   count unchanged

EX 31536000 = one year, after which the key deletes itself and the visitor could like again. Both steps run in one Lua script (see Redis · 01), so two fast clicks can't both pass.

4. The three layers

LayerWhereJob
Visitor keyRedisThe real lock. Can't be bypassed by clearing the browser.
localStorageBrowserKeeps the heart filled on reload and skips useless requests. Easy to clear, so never trusted alone.
Rate limitRedis (@upstash/ratelimit)Max 5 requests/min per IP. Stops bots hammering the API. Not the duplicate check.

5. Limits of this approach

Without sign-in, no website can identify a person, only a network + browser:

  • Different browser, VPN or mobile data → new IP or user-agent → counts as a new visitor.
  • Two people, same Wi-Fi, identical browser → same ID → counted once.

For a like counter that's an acceptable trade-off. Only login guarantees one per person.

In one line

The server hashes IP + browser + a secret into a visitor ID, and Redis SET NX lets that ID add +1 only once a year.

Redis · 03

How much load polling puts on Redis

1. Reads vs writes

Every visitor's button asks for the count every 10 seconds. That sounds like a lot of Redis traffic, but it splits into two very different kinds:

RequestRedis commandsHow often Redis sees it
GET (poll)GET likes:siteAt most once per 10s per Vercel region. The CDN answers everyone else (see Vercel · 01).
POST (like)Lua script: SET NX + INCR, plus rate-limit commandsEvery time, never cached. Rare: once per visitor.

2. The maths

# reads, worst case: a visitor polling every second of the month, one region
60/10 × 60 × 24 × 30  = ~259,200 GETs/month

# Upstash free tier
500,000 commands/month

That's the ceiling whether 1 or 10,000 people have the tab open, because the cache, not the visitor count, decides how often Redis is hit. In practice it's far lower: when nobody is on the site, nothing is polled.

3. Why GET is cheap for Redis anyway

GET on one key reads a value already in memory. It takes microseconds, and nothing is locked or rewritten. Even uncached, Redis could handle many thousands per second. The cache mainly saves the free-tier command count and the network trip, not Redis's CPU.

In one line

Polling reads are capped by the CDN cache at about one per 10s per region, so Redis load stays tiny no matter how many visitors are watching.

Vercel · 01

Serverless functions and the CDN cache

1. What a serverless function is

On Vercel, /api/likes isn't a server that's always running. It's a function that starts when a request arrives, answers and can be shut down soon after. Consequences:

  • No memory between requests: a variable like let count = 0 resets whenever the function restarts. That's why the count lives in Redis.
  • Several copies at once: under traffic Vercel runs many copies in parallel, each with its own memory.
  • Short lives: functions have a time limit and are billed while running, so holding a connection open for minutes (WebSockets, long streams) is expensive or impossible.

2. The CDN cache in front of it

Vercel puts a CDN (copies of responses stored in data centres near visitors) in front of every function. The function controls it with one response header:

Cache-Control: public, s-maxage=10, stale-while-revalidate=60
PartMeaning
publicThe same answer can be shared by all visitors (fine for a total count).
s-maxage=10The CDN may reuse the answer for 10 seconds without calling the function.
stale-while-revalidate=60For up to 60s after that, the CDN serves the old answer instantly and refreshes it in the background.

3. What it looks like over time

0s   visitor A → CDN empty → function → Redis → 42   (stored)
3s   visitor B → CDN       → 42                       (no function call)
9s   visitor C → CDN       → 42
12s  visitor D → CDN       → 42 (stale) + refresh in background → 45
14s  visitor E → CDN       → 45

4. Why the poll interval is 10 seconds

The cached answer only changes every 10s, so polling faster just returns the same number. 10s matches s-maxage: it's the fastest interval that can show anything new.

5. What must never be cached

The POST (the like itself) changes data and returns a per-visitor answer, so it sends Cache-Control: no-store. Per-visitor info like "did I like it" can't go in the shared GET either, or one visitor's answer would be served to everyone. That's why "liked" is kept in the browser's localStorage.

In one line

Vercel functions are short-lived and stateless, and the CDN cache (s-maxage) lets thousands of visitors share one answer per 10 seconds.

Real-time UI · 01

Updating a count live without refreshing

1. Three ways to get updates from a server

ApproachHowTrade-off
PollingThe browser asks again every N seconds.Simple, works anywhere, cacheable. Up to N seconds late.
Server-Sent EventsThe browser opens one long HTTP response; the server writes a line whenever something changes.Instant, one-way. Needs a long-running connection.
WebSocketsA permanent two-way connection.Instant, both ways. Needs a server that stays up, or a paid service (Pusher, Ably).

On serverless (see Vercel · 01) long connections are costly, and a like count doesn't need to be instant. Polling every 10 seconds is the right fit.

2. The polling loop

setInterval(() => {
  if (document.hidden || saving) return;      // skip in background tabs / mid-like
  fetch("/api/likes").then(r => r.json()).then(d =>
    setCount(c => Math.max(c, d.count))       // never go down
  );
}, 10_000);

3. Pausing in hidden tabs

The browser fires a visibilitychange event when a tab is hidden or shown, and document.hidden says which. The button stops polling when hidden (no point updating a number nobody sees) and checks immediately when the tab comes back, so the visitor never sees a stale count.

4. Why the count takes the higher number

Likes are never removed, so the true count only grows. But a poll can return a cached answer that's older than what the button already shows:

you like       → POST returns 43         (fresh)
next poll      → CDN still has 42       (cached before your like)
Math.max(43, 42) → 43                 no flicker back down

The same idea is why polls are skipped while your own like is saving: a reply landing mid-save could undo the instant +1.

5. Showing the change

When a poll brings a higher number, a counter (bump) goes up. Using it as the React key remounts the number, so Framer Motion replays a slide-up, and the heart pulses. For visitors with reduced motion, the number just changes.

In one line

Poll every 10s while the tab is visible, keep the higher of local and server counts, and animate only when the number really grows.
