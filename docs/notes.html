Redis · 01

How Redis stores the like count on Vercel

1. What Redis is

Redis is a key–value database that keeps all its data in memory (RAM), so reads and writes take well under a millisecond. Every value lives under a name (a key), like a giant dictionary:

likes:site        → "1234"      # the total count
like:v:9f2c…e1    → "1"         # "this visitor already liked"

Data in RAM would vanish on restart, so Redis also writes it to disk in the background. Upstash (the hosted Redis we use) handles this for us.

2. How the count is stored

The count is a plain string holding a number. Redis notices it looks like an integer and stores it compactly as one. You never read it, add 1 and write it back yourself. You send one command:

INCR likes:site    # 1234 → 1235, returns 1235

If the key doesn't exist yet, INCR treats it as 0 and makes it 1.

3. Why no click is ever lost

Redis runs commands one at a time, on a single thread. Even if 1,000 requests arrive together, they wait in a queue and each INCR finishes completely before the next starts. So it's impossible for two clicks to both see 1234 and both write 1235.

# what goes wrong with read-then-write (any database):
A reads 1234 · B reads 1234 · A writes 1235 · B writes 1235   → one like lost

# Redis INCR, queued one after another:
A: INCR → 1235 · B: INCR → 1236                               → both counted

4. One like per visitor: SET NX

SET key 1 NX writes the key only if it doesn't exist (NX = "not exists"). The first time a visitor likes, it succeeds; every later try fails. EX 31536000 deletes the key after a year. The visitor key is a hash of IP + browser + a secret, so no real IP is stored.

The check and the +1 must happen together. Redis runs a small Lua script as one uninterrupted step, so nothing can sneak in between:

if redis.call('SET', KEYS[1], 1, 'NX', 'EX', 31536000) then
  return {1, redis.call('INCR', KEYS[2])}   -- new visitor → +1
end
return {0, redis.call('GET', KEYS[2])}       -- already liked → just the count

5. How Vercel talks to it

On Vercel, the API route (/api/likes) runs as a serverless function: it starts for a request, answers and may be shut down right after. A normal Redis client keeps a TCP connection open, and those connections leak or run out when functions keep starting and stopping.

Upstash solves this by accepting Redis commands over plain HTTPS. Each command is one independent web request, so nothing stays open:

Browser ──POST /api/likes──▶ Vercel function ──HTTPS──▶ Upstash Redis
                                 │                       runs the Lua script
        ◀──── { count } ─────────┘◀───── 1235 ───────────┘

The function finds the database through two environment variables that Vercel adds when you connect Upstash from its Marketplace: KV_REST_API_URL (where) and KV_REST_API_TOKEN (the password). They stay on the server and never reach the browser.

In one line

Redis keeps the count in memory as one number, INCR and a Lua script make every update a single uninterruptible step, and Upstash lets short-lived Vercel functions reach it over HTTPS.
